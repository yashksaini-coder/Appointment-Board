## 1. Before you deploy anything

The local setup makes choices that are wrong in production. Change these first.

| #   | Change                                 | Why                                                                               |
| --- | -------------------------------------- | --------------------------------------------------------------------------------- |
| 1   | `SEED_SAMPLE_DATA=false`               | Otherwise an empty production database gets seven fake appointments on first boot |
| 2   | Replace `create_all` with migrations   | `create_all` never alters an existing table, so the schema silently drifts        |
| 3   | Drop `--reload`, add `--workers`       | `--reload` is a development file watcher                                          |
| 4   | Real `POSTGRES_PASSWORD`               | The default is `appointments`                                                     |
| 5   | `CORS_ORIGINS` = your real domain only | The default allows `localhost`                                                    |
| 6   | `LOG_FORMAT=json`                      | So a log aggregator can parse it                                                  |
| 7   | Managed PostgreSQL, not a container    | The compose `db` service has no backups or failover                               |
| 8   | TLS everywhere                         | Both the site and the database connection (`?sslmode=require`)                    |

### Environment variables

```bash
DATABASE_URL=postgresql+psycopg://user:pass@host:5432/dbname?sslmode=require
CORS_ORIGINS=https://board.example.com
LOG_LEVEL=INFO
LOG_FORMAT=json
SEED_SAMPLE_DATA=false
DB_POOL_SIZE=5
DB_MAX_OVERFLOW=10
```

`DATABASE_URL` accepts `postgres://`, `postgresql://` or `postgresql+psycopg://`
— the app rewrites the first two to the driver it actually installs, which is
the single most common managed-database boot failure.

> **Connection budget.** Total connections = `workers × (DB_POOL_SIZE + DB_MAX_OVERFLOW)`.
> Four workers at the defaults is 60 connections. A small managed Postgres often
> caps at 22–25, so either lower the pool or add PgBouncer.

## 2. Migrations (replace `create_all`)

`Base.metadata.create_all()` creates missing tables and does nothing else. The
first time you add a column it will not appear, and you will not be told.

```bash
cd backend
pip install alembic
alembic init migrations
```

**`migrations/env.py`** — point Alembic at the models and the live URL:

```python
import os
from app.db import Base, _with_driver
from app import models  # noqa: F401  — registers the tables on Base

config.set_main_option("sqlalchemy.url", _with_driver(os.environ["DATABASE_URL"]))
target_metadata = Base.metadata
```

Generate and apply the first revision:

```bash
alembic revision --autogenerate -m "initial schema"
alembic upgrade head
```

> ### The gotcha that will bite you
>
> **Alembic's autogenerate does not emit the exclusion constraint.** It handles
> tables, columns, indexes and most constraints, but `ExcludeConstraint` is not
> detected — so the generated migration silently omits the one thing preventing
> double bookings. Add it to the migration by hand:
>
> ```python
> def upgrade():
>     # ... autogenerated table creation ...
>     op.execute("""
>         ALTER TABLE appointments ADD CONSTRAINT no_overlapping_appointments
>         EXCLUDE USING gist (
>           tsrange(appointment_date + start_time,
>                   appointment_date + end_time, '[)') WITH &&
>         ) WHERE (status <> 'cancelled')
>     """)
>
> def downgrade():
>     op.execute("ALTER TABLE appointments DROP CONSTRAINT no_overlapping_appointments")
> ```
>
> Verify after deploying: `\d appointments` in `psql` must list the constraint.
> If it is missing, the API still returns 409s from its own check, but
> concurrent requests can double-book and nothing will tell you.

Then remove the line from `backend/app/main.py`:

```python
Base.metadata.create_all(engine)   # delete once Alembic owns the schema
```

**Run migrations as a deploy step, never at app startup.** With more than one
worker or replica, several processes would race to migrate the same database.
Use a release command, an init container, or a one-off task — each platform
section below shows where.

## 3. Production Dockerfile

The existing `backend/Dockerfile` works; this version drops root and runs
workers. Save as `backend/Dockerfile.prod`, or edit in place.

```dockerfile
FROM python:3.12-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

WORKDIR /app

RUN adduser --disabled-password --gecos "" appuser

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .
USER appuser

EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--workers", "4"]
```

- Start at **2 workers per CPU core**, then measure. The API is I/O-bound.
- Endpoints are sync `def`, so each worker also has a threadpool. That is why
  the connection budget above matters.
- The frontend `Dockerfile` is already a multi-stage build ending in nginx and
  needs no change.

> **Building on Apple Silicon for an x86 host?** Add `--platform linux/amd64`,
> or the container will fail to start with an exec-format error.
>
> ```bash
> docker buildx build --platform linux/amd64 -t api ./backend
> ```

## 4. Deploy: Vercel + a managed API

Vercel hosts the React frontend. **Run the FastAPI backend somewhere else** —
Vercel's Python runtime is serverless, and a new process per request means a new
SQLAlchemy pool per request, which exhausts database connections quickly. Use
DigitalOcean App Platform, AWS App Runner, Render, Fly.io or Railway for the API.

### Frontend on Vercel

In the Vercel dashboard, import the repo and set:

| Setting          | Value           |
| ---------------- | --------------- |
| Root Directory   | `frontend`      |
| Framework Preset | Vite            |
| Build Command    | `npm run build` |
| Output Directory | `dist`          |
| Install Command  | `npm ci`        |

Add an environment variable:

```
VITE_API_URL = https://api.example.com/api
```

> **`VITE_*` variables are baked in at build time, not read at runtime.**
> Changing the value requires a redeploy, and the value is visible in the
> shipped JavaScript. Never put a secret in one.

Create **`frontend/vercel.json`**:

```json
{
  "rewrites": [
    {
      "source": "/api/:path*",
      "destination": "https://api.example.com/api/:path*"
    },
    { "source": "/(.*)", "destination": "/index.html" }
  ]
}
```

The first rewrite is the useful one: Vercel proxies `/api` to your backend, so
the browser only ever sees one origin and **there is no CORS at all**. With it
in place, leave `VITE_API_URL` unset — the app defaults to the relative `/api`.

The second rewrite serves `index.html` for unknown paths, which a single-page
app needs.

### If you skip the proxy

Then it _is_ cross-origin, and the backend must allow it:

```bash
CORS_ORIGINS=https://board.example.com,https://board-git-main-you.vercel.app
```

Vercel preview deployments get a new hostname per branch, so a fixed list will
not cover them. Either add a regex in `backend/app/main.py`:

```python
app.add_middleware(
    CORSMiddleware,
    allow_origins=os.getenv("CORS_ORIGINS", "").split(","),
    allow_origin_regex=r"https://.*-yourteam\.vercel\.app",
    ...
)
```

…or use the proxy and avoid the problem.

### Deploy

```bash
npm i -g vercel
cd frontend
vercel            # preview
vercel --prod     # production
```

Or just push to `main` — Vercel deploys on push once the repo is connected.

## 5. Deploy: DigitalOcean

Two routes. **App Platform** is managed and deploys from the repo. **A Droplet**
is a plain VM running the compose file you already have.

### 5a. App Platform (recommended)

**Managed database first.** Create → Databases → PostgreSQL 16. Copy the
connection string; it looks like:

```
postgresql://doadmin:PASSWORD@db-postgresql-xxx.ondigitalocean.com:25060/defaultdb?sslmode=require
```

Add your app as a **Trusted Source** on the database's Settings tab, or
connections are refused.

Commit **`.do/app.yaml`**:

```yaml
name: appointment-board
region: nyc

databases:
  - name: db
    engine: PG
    version: "16"
    production: true

services:
  - name: api
    github:
      repo: your-user/appointment-board
      branch: main
      deploy_on_push: true
    source_dir: backend
    dockerfile_path: backend/Dockerfile
    http_port: 8000
    instance_size_slug: basic-xxs
    instance_count: 1
    health_check:
      http_path: /api/health
      initial_delay_seconds: 20
    # Runs once per deploy, before the new version takes traffic.
    run_command: alembic upgrade head && uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 2
    envs:
      - key: DATABASE_URL
        scope: RUN_TIME
        value: ${db.DATABASE_URL}
      - key: CORS_ORIGINS
        scope: RUN_TIME
        value: ${APP_URL}
      - key: LOG_FORMAT
        scope: RUN_TIME
        value: json
      - key: SEED_SAMPLE_DATA
        scope: RUN_TIME
        value: "false"
    routes:
      - path: /api

static_sites:
  - name: web
    github:
      repo: your-user/appointment-board
      branch: main
    source_dir: frontend
    build_command: npm ci && npm run build
    output_dir: dist
    catchall_document: index.html
    routes:
      - path: /
```

```bash
doctl apps create --spec .do/app.yaml
doctl apps list
doctl apps logs <app-id> --type run --follow
```

Because the API is routed at `/api` and the site at `/`, they share one origin
and CORS never applies.

> `${db.DATABASE_URL}` is injected as `postgresql://…`. The app rewrites that to
> the psycopg 3 driver automatically — without that rewrite this is where the
> deploy fails with `ModuleNotFoundError: psycopg2`.

### 5b. Droplet + Docker Compose

For a small team this is cheap and completely transparent.

```bash
# On a fresh Ubuntu droplet
curl -fsSL https://get.docker.com | sh
git clone https://github.com/your-user/appointment-board.git
cd appointment-board
cp .env.example .env && nano .env      # real password, SEED_SAMPLE_DATA=false
docker compose -f docker-compose.prod.yml up -d
```

**`docker-compose.prod.yml`** — no bind mounts, no reload, no exposed database:

```yaml
services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: ${POSTGRES_DB}
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER}"]
      interval: 5s
      retries: 20
    restart: always
    # note: no `ports:` — the database is not reachable from the internet

  backend:
    build: ./backend
    environment:
      DATABASE_URL: postgresql+psycopg://${POSTGRES_USER}:${POSTGRES_PASSWORD}@db:5432/${POSTGRES_DB}
      CORS_ORIGINS: https://board.example.com
      LOG_FORMAT: json
      SEED_SAMPLE_DATA: "false"
    command: >
      sh -c "alembic upgrade head &&
             uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 4"
    depends_on:
      db:
        condition: service_healthy
    restart: always

  frontend:
    build: ./frontend
    depends_on: [backend]
    restart: always

  caddy:
    image: caddy:2-alpine
    ports: ["80:80", "443:443"]
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile
      - caddy_data:/data
    depends_on: [frontend]
    restart: always

volumes:
  pgdata:
  caddy_data:
```

**`Caddyfile`** — automatic HTTPS, certificate included:

```
board.example.com {
    reverse_proxy frontend:80
}
```

Point the domain's A record at the droplet, and Caddy obtains a Let's Encrypt
certificate on first request. Back up the database on a schedule:

```bash
docker compose exec -T db pg_dump -U appointments appointments | gzip > backup-$(date +%F).sql.gz
```

## 6. Deploy: AWS

Two routes again: **App Runner** is the short path, **ECS Fargate** the
controllable one. Both use RDS and ECR.

### 6a. Database — RDS

Console → RDS → Create database → PostgreSQL 16.

- Start with `db.t4g.micro`, 20 GB gp3.
- **Not publicly accessible.** Put it in private subnets.
- Create a security group allowing port 5432 **only from the app's security
  group**, not from `0.0.0.0/0`.
- Turn on automated backups (7 days) and Performance Insights.
- Store the connection string in Secrets Manager:

```bash
aws secretsmanager create-secret \
  --name appointment-board/database-url \
  --secret-string 'postgresql+psycopg://appuser:PASSWORD@xxx.rds.amazonaws.com:5432/appointments?sslmode=require'
```

### 6b. Image — ECR

```bash
export ACCOUNT=123456789012 REGION=eu-west-1
aws ecr create-repository --repository-name appointment-board-api --region $REGION

aws ecr get-login-password --region $REGION \
  | docker login --username AWS --password-stdin $ACCOUNT.dkr.ecr.$REGION.amazonaws.com

docker buildx build --platform linux/amd64 -t appointment-board-api ./backend
docker tag appointment-board-api:latest \
  $ACCOUNT.dkr.ecr.$REGION.amazonaws.com/appointment-board-api:latest
docker push $ACCOUNT.dkr.ecr.$REGION.amazonaws.com/appointment-board-api:latest
```

### 6c. API — App Runner (simplest)

Console → App Runner → Create service → Container registry → your ECR image.

| Setting           | Value                                                                 |
| ----------------- | --------------------------------------------------------------------- |
| Port              | `8000`                                                                |
| Health check path | `/api/health`                                                         |
| Environment       | `LOG_FORMAT=json`, `SEED_SAMPLE_DATA=false`, `CORS_ORIGINS=https://…` |
| Secret            | `DATABASE_URL` from Secrets Manager                                   |
| VPC connector     | **Required** to reach a private RDS instance                          |

App Runner gives you HTTPS and autoscaling with no load balancer to configure.
Run migrations once from a machine that can reach the database:

```bash
DATABASE_URL='postgresql+psycopg://…' alembic upgrade head
```

### 6d. API — ECS Fargate (more control)

1. **Cluster** → Networking only (Fargate).
2. **Task definition** — awsvpc, 0.5 vCPU / 1 GB, your ECR image, container
   port 8000, `DATABASE_URL` from Secrets Manager, logs to CloudWatch:
   ```json
   "logConfiguration": {
     "logDriver": "awslogs",
     "options": {
       "awslogs-group": "/ecs/appointment-board",
       "awslogs-region": "eu-west-1",
       "awslogs-stream-prefix": "api"
     }
   }
   ```
3. **ALB** — target group on port 8000, health check path `/api/health`,
   HTTPS listener with an ACM certificate.
4. **Service** — 2 tasks across two AZs, attached to the target group.
5. **Migrations** — a one-off task with the same definition:
   ```bash
   aws ecs run-task --cluster appointment-board --task-definition appointment-board-api \
     --launch-type FARGATE --network-configuration "…" \
     --overrides '{"containerOverrides":[{"name":"api","command":["alembic","upgrade","head"]}]}'
   ```

Because logs are JSON, CloudWatch Logs Insights can query them directly:

```
fields @timestamp, fields.status, fields.duration_ms, request_id
| filter event = "request" and fields.status >= 400
| sort @timestamp desc
```

### 6e. Frontend — S3 + CloudFront

```bash
cd frontend && npm ci && npm run build
aws s3 sync dist/ s3://board-example-com --delete
aws cloudfront create-invalidation --distribution-id EXXXX --paths "/*"
```

- S3 bucket private; serve through CloudFront with Origin Access Control.
- **SPA routing:** add a custom error response mapping **403 and 404 → `/index.html`
  with status 200**, or any deep link returns an error page.
- Add a second CloudFront origin for the ALB/App Runner URL with a
  `/api/*` behaviour. Same origin in the browser, no CORS.

## 7. Deploy: any Docker host

The portable path — works on Render, Fly.io, Railway, Hetzner, a bare VM, or a
Kubernetes cluster.

```bash
# 1. Build both images for the target architecture
docker buildx build --platform linux/amd64 -t ghcr.io/you/board-api:1.0.0 ./backend
docker buildx build --platform linux/amd64 -t ghcr.io/you/board-web:1.0.0 ./frontend

# 2. Push to a registry
echo $GITHUB_TOKEN | docker login ghcr.io -u you --password-stdin
docker push ghcr.io/you/board-api:1.0.0
docker push ghcr.io/you/board-web:1.0.0

# 3. On the host
docker pull ghcr.io/you/board-api:1.0.0
docker run -d --name api --restart always -p 8000:8000 \
  -e DATABASE_URL='postgresql+psycopg://…?sslmode=require' \
  -e CORS_ORIGINS='https://board.example.com' \
  -e LOG_FORMAT=json -e SEED_SAMPLE_DATA=false \
  ghcr.io/you/board-api:1.0.0
```

**Tag real versions, never deploy `:latest`** — you cannot roll back to a tag
that keeps moving.

### Build and push from GitHub Actions

```yaml
name: deploy
on:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    permissions: { contents: read, packages: write }
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          context: ./backend
          push: true
          tags: ghcr.io/${{ github.repository }}-api:${{ github.sha }}
```

Run the test suite in CI before that job — it needs a PostgreSQL service
container, because the exclusion constraint does not exist in SQLite:

```yaml
services:
  postgres:
    image: postgres:16-alpine
    env:
      POSTGRES_USER: appointments
      POSTGRES_PASSWORD: appointments
      POSTGRES_DB: appointments
    options: >-
      --health-cmd pg_isready --health-interval 5s --health-retries 10
    ports: ["5432:5432"]
```

## 8. Post-deploy checklist

Run these against the live deployment, not localhost.

```bash
# Health
curl -s https://api.example.com/api/health          # {"status":"ok"}

# The constraint actually exists — the single most important check
psql "$DATABASE_URL" -c '\d appointments' | grep no_overlapping_appointments

# The API rejects an overlap
curl -s -o /dev/null -w '%{http_code}\n' -X POST https://api.example.com/api/appointments \
  -H 'Content-Type: application/json' \
  -d '{"title":"A","description":"","appointment_date":"2030-01-01","start_time":"09:00","end_time":"10:00"}'
# repeat the same call — expect 201 then 409

# Request tracing works end to end
curl -s -D- -o /dev/null https://api.example.com/api/health -H 'X-Request-Id: smoke-test-1' | grep -i x-request-id
```

| Check                | Looking for                                          |
| -------------------- | ---------------------------------------------------- |
| `/api/health`        | `{"status":"ok"}`                                    |
| Exclusion constraint | Present in `\d appointments`                         |
| No sample data       | The board is empty, not showing "Team standup"       |
| HTTPS                | Valid certificate, HTTP redirects to HTTPS           |
| Database             | Not reachable from the public internet               |
| Backups              | Automated, and a restore actually tested             |
| Logs                 | JSON, arriving in your aggregator, with `request_id` |
| CORS                 | Your domain only — not `*`, not `localhost`          |
| Secrets              | In a secret store, not in the image or the repo      |
| Alerting             | On `level=ERROR` and on `event=db.unavailable`       |

### What to watch

The logging is designed so the useful queries are one filter away:

| Question                              | Filter                                            |
| ------------------------------------- | ------------------------------------------------- |
| Is anything failing?                  | `level = "ERROR"`                                 |
| Are users hitting slot conflicts?     | `event = "appointment.slot_conflict"`             |
| Did a race beat the pre-flight check? | `event = "appointment.rejected_by_database"`      |
| Is the API slow?                      | `event = "request"`, chart `fields.duration_ms`   |
| Did production start empty?           | `event = "db.seeded"` — an alarm, not a milestone |
